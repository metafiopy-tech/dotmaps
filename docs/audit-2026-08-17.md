# DOT MAPS — Technical & Product Diligence Audit

Repository-wide review across `main`, `queen-v0`, `queen-watch`, `queen-v1`, and
`queen-os`. Prepared 17 August 2026.

Committed verbatim from `Dot_Maps_Technical_Product_Diligence_Audit_2026-08-17.docx`
per `HARDENING_BRIEF.md`'s G0 step — a faithful transcription (document order,
headings, tables, footnote markers), not a paraphrase.

> **Bottom line.** Dot Maps is strongest today as a research instrument for
> mechanically verifying agent work and reusing certified procedures. Queen OS is a
> promising product shell, but the current queen-os branch should not be treated as
> production-safe until the chat proof boundary, agent sandbox, network fetch
> policy, and append-only ledger concurrency are hardened.

Audit basis: public GitHub repository and branch comparisons as available on 17 Aug
2026. The review environment could read raw GitHub files but could not clone/execute
the repository due to outbound DNS restrictions, so test results cited here are
repository-recorded results, not independently rerun results. This is a technical
diligence review, not a security certification.

## Executive verdict

> **What it is first.** Research artifact / verification instrument first;
> developer framework second; product prototype third. The project itself calls
> the core a harness, while Queen OS is a newer product layer built on top of that
> research spine.

**Strongest claim:** An agent can be separated from the authority that decides
whether its work is complete. Dot Maps makes world-state checks sovereign, records
the evidence, and can replay certified procedures without calling a model.

**Weakest current claim:** That the newest Queen chat experience is itself
mechanically verified end-to-end. The current gate validates the structure of
`answer.json` but not the proposed predicate/value before returning the free-form
answer, and the free-form answer is not mechanically bound to the checked fact.

**Product readiness:** Good research/demo quality; not yet safe as an unattended
general-purpose agent on a normal workstation containing credentials or valuable
files.

| Area | Assessment | Why |
| --- | --- | --- |
| Core verification idea | 9/10 | Coherent laws, live failure cases, adversarial gates, replayable evidence. |
| Experimental discipline | 9/10 | Pre-registration, published negative result, bundled journals; independent replication still absent. |
| Learning / skill bank | 7.5/10 | Real candidate -> oracle -> replay path, but certification statistics/context need hardening. |
| Queen OS product layer | 7/10 | Clear route-first UX and live demo; sample-data limits and proof-binding bug remain. |
| Security boundary | 4.5/10 | Core ToolBox is thoughtful; full Claude work order bypasses that safety model and Watch has SSRF exposure. |
| Concurrency / durability | 5/10 | Readable JSONL design, but hash-chain writes are non-atomic under concurrent requests. |
| Production readiness | 5.5/10 | Useful prototype, not yet a hardened always-on service. |

- **main** — strongest stable research baseline: experiments, grow loop,
  verification and safety spine.
- **queen-watch** — adds work orders, operator UI/assurance, and point-and-watch

### Highest-priority audit findings

| Pri | Finding | Why it matters | Recommended fix |
| --- | --- | --- | --- |
| P0 | Verified-chat boundary is incomplete | `queen/chat.py` `_chat_gate()` checks JSON shape/path/predicate name but does not evaluate predicate/value; `ask()` returns answer text even when `banking.confirm()` fails. Free-form answer is also not mechanically entailed by the checked statement. | Make checked result the source of the reply. Require `claude_result.ok`, validate+confirm before any answer is returned, and deterministically render the user reply from verifier output / typed result rather than trusting a free-form answer field. |
| P0 | Full-agent work order is not sandboxed | `queen/workorder.py` and `queen/chat.py` run `claude -p` with `--dangerously-skip-permissions`. cwd is treated as a containment boundary, but a working directory is not OS isolation. | Run work orders in a real sandbox/container/VM with only the temp workspace mounted writable, network denied by default, CPU/time limits, and explicit tool/network grants. |
| P0 | Secrets can leak into the full-agent child | The child environment removes `ANTHROPIC_API_KEY` but passes every other environment variable to the agent process. Bash/tool access can expose unrelated tokens or credentials. | Use an empty/allowlisted environment; broker credentials per tool; never expose host env wholesale. Add a regression test with planted secrets. |
| P0 | Watch/fetch SSRF exposure | `runtime/traveler.py` `fetch.get` accepts any http(s) URL and urllib follows it; there is no block for localhost, private/link-local/metadata IPs, redirects or DNS rebinding. | Central SafeFetcher: resolve and require globally routable addresses, block private/link-local/loopback/reserved ranges, revalidate every redirect, restrict ports/schemes, cap bytes/time. |
| P1 | Hash-chain append is race-prone | `queen/trips.py` and chat ledger do read-tail -> compute seq/hash -> append with no lock. Threaded UI requests can fork the chain or duplicate sequence numbers. | Make append atomic with process-safe file locking + fsync, or append to SQLite WAL while preserving an immutable export journal. Add a concurrent-writer stress test. |
| P1 | Skill certification uses pseudo-replication | `bank/certify.py` runs 20 deterministic replays, largely against the same seed copy. A Wilson interval on repeated identical deterministic trials does not establish broad reliability/generalization. | Either call this replay consistency (not statistical confidence), or probe independent perturbed/fresh environments with a declared sampling model before using Wilson as a reliability bound. |
| P1 | Certification can be order-dependent | `certify_all()` copies the seed once, then all skills and 20 probes reuse it. Mutation skills can change the shared seed and influence later skills. | Fresh workspace per skill and preferably per probe; keep oracle mutation test isolated. Pin formation-context fingerprints per skill. |
| P1 | Sleep can reset a failed re-cert | `sleep()` collects due skills, calls `certify_all()`, then resets every due card and logs `action=re-certified` without checking the post-cert status. | Only reset cards whose new status is certified. Failed rechecks should emit CONVICTED/ORACLE_FAIL, remain stale/demoted, and never get a success event. |
| P1 | FSRS-lite stability currently cancels out | `due_for_recheck` compares `stability*freshness` against `stability*threshold`, so stability mathematically cancels. Every used card goes due at the same freshness ratio regardless of invocation count. | Make stability affect decay/review interval, or rename the mechanism honestly as fixed-age recheck until fitted data exists. |
| P1 | Identity collisions | Watch target slug uses netloc only; chat learned-map slug truncates the normalized question to 40 chars. Different targets/questions can share persistent namespaces. | Readable prefix + short hash of full normalized URL/message for every persistent ID. |
| P2 | Global seed/context does not scale to multiple domains | Queen sleep defaults to `corpus/pilot/seed-ws`, while skills do not yet carry a fully enforced formation environment / invalidation context. | Attach context fingerprint + seed/provider reference + invalidation predicate to each skill; recertify against its own domain context. |
| P2 | Product data plane needs separation from audit log | Files/JSONL are excellent research evidence but weak for concurrent product state, migrations, indexing and multi-user access. | Keep append-only evidence as source-of-truth artifact, but add a transactional indexed projection (SQLite first) for UI/product state. |

## Diligence questions

### Positioning

**1. In one sentence, what does it do that Claude/ChatGPT alone does not?**
[High confidence] It separates generation from authority: an agent can propose or
perform work, but independent executable checks decide whether the work is true,
then certified procedures can be replayed later with no model call.
Evidence: README five rules; `bank/route.py`; verifier architecture. [S01, S08]

**2. Is this a product, a research artifact, or a framework — and which one is it
first?**
[High confidence] It is a research artifact / verification instrument first, a
developer framework second, and a product prototype third. The oldest and
best-supported layer is the harness and its experiments; Queen OS is a newer
product shell over that spine.
Evidence: README calls it a harness; campaign and STATUS are experiment ledgers;
Queen OS product layer appears in the Aug 17 branch commits. [S01, S02, S04, S14]

**3. Who is it for on day one: you, developers, or my grandmother?**
[High confidence] Developers and the builder. The Queen UI is explicitly trying to
hide jargon, but installation, Claude/Ollama/Docker/MCP setup, verifier semantics,
sample-workspace assumptions and current security constraints make it unsuitable
for a nontechnical grandmother on day one.
Evidence: Queen OS PRD/UI commits; pyproject; current chat job is hard-coded to a
small sample dataset. [S06, S14, S15]

**4. What's the elevator demo — the 60 seconds that makes me get it?**
[High confidence] Best product demo: ask a pre-covered question and show
"$0 - certified replay"; ask one new checkable question and show the model work
once; approve "learn it"; run the certification/sleep step; ask the exact question
again and show the same result at $0 with the model runner never called. Best
research demo: replay the bundled 3B false-success run and watch the agent claim
success while the board stays red.
Evidence: Queen OS live flight records a $0.0776 new ask -> learn -> sleep -> same
ask at $0; README provides two-minute offline replay of lying agents. [S01, S14]

### Capabilities & limits

**5. What can I point it at today and expect success? Give me the honest list.**
[High confidence] Today I would expect success only where the world-state can be
reduced to narrow deterministic checks: the bundled filesystem maps; the 5-dot
content migration; exact-match certified skill replay; GET-only static-site health
checking through Watch; scripted or Ollama travelers on the proven maps; and
explicitly bound MCP tools when a map grants them. Queen Chat itself is still a
demo-workspace Q&A path and is not yet linked-folder-aware.
Evidence: STATUS live migration; Watch compiler scope; Queen OS live flight known
limit. [S02, S14, S13]

**6. What will it fail at, and does it fail loudly or quietly?**
[High confidence] It will fail on open-ended work with no enforceable oracle,
dynamic/browser-heavy or authenticated sites outside the Watch predicate set,
semantic/generalized routing, opinions, broad linked-folder chat, and many
frontier tasks local small models cannot solve. The core harness usually fails
loudly by keeping dots red or returning FRONTIER/ORACLE_FAIL; however, current
Queen Chat has a quiet correctness leak because it can return a free-form answer
even when the later discriminating confirmation fails.
Evidence: README honest limits; Watch scope; Queen chat `ask()` control flow.
[S01, S13, S07]

**7. "Certified" - certified against what? Who defines correct?**
[High confidence] Certified means "passed this frozen check under this
certification procedure," not "objectively true in every context." Map
correctness is defined by its dot verifiers and attack/probe regime; skill
correctness is defined by the stored predicate/check, an oracle discrimination
gate, and deterministic replay. Ultimately the map/check author or compiler
defines the target, so specification error remains outside the certificate.
Evidence: README; `bank/certify.py`; `grow/banking.py`. [S01, S09, S10]

**8. What happens in domains where no ground truth exists (opinions, aesthetics,
contested claims)?**
[High confidence] Dot Maps should abstain from claiming objective certification.
It can certify adherence to a human-defined rubric or measurable proxy, but that
is "certified to the rubric," not a proof that an opinion or aesthetic judgment is
correct. If no defensible external criterion exists, the honest state is
frontier/human judgment.
Evidence: Inference from the sovereign-verifier design and fixed predicate
architecture. [S01, S10]

**9. Can it do things, or only check things? Where's the line between watch,
verify, and act?**
[High confidence] It can do things. The core traveler executes whitelisted
filesystem/fetch/MCP actions; a certified skill replays frozen method steps; a
work order runs an agent to mutate a disposable workspace; verifiers only judge;
Watch is intended to observe via GET and run health predicates. The design line
is: Act changes state, Verify judges state, Watch repeatedly observes state.
Evidence: `runtime/traveler.py` ToolBox; `bank/route.py`; `workorder.py`; Watch
compiler. [S08, S11, S12, S13]

**10. If the world changes after certification, how fast does it notice it's
wrong?**
[High confidence] On a covered skill, the stored check is rerun when that skill is
invoked, so an observable violation can be noticed immediately on the next replay.
Watch can notice on its configured poll interval (the live example used 60
minutes). The generic decay path is not real-time: the current fixed freshness
math goes due around 48 days after last use, and rechecks are cron-ready rather
than an always-on daemon. Semantic drift that the verifier does not encode may
never be noticed.
Evidence: `route.py` reruns check; Watch live acceptance; `reconsolidate.py`
30-day exponent / 0.2 threshold; sleep is cron-ready. [S08, S14, S16, S17]

**11. What's the largest task it's completed end-to-end without a human? The
smallest it's failed?**
[High confidence] The largest clearly documented autonomous product-style task is
the 5-dot content migration: qwen2.5-coder:7b completed it end-to-end in 2 cycles,
1m54s, $0, with all five verifiers green. There is no formal task-size scale for
the "smallest failed" claim; documented small-model floors include a 3B anchor at
0/5 and qwen3:8b that repeatedly ate only 1/5 dots. Treat those as examples, not a
calibrated minimum.
Evidence: STATUS Phase 3 and experiment layer. [S02]

### The learning loop

**12. How does it "learn a skill" mechanically - what is actually stored?**
[High confidence] It does not update model weights. A banked primitive becomes a
YAML skill card containing a statement, exact trigger key, frozen method steps
plus a hash, a predicate/value check, required tools, provenance, certificate
fields and decay/usage metadata. It enters as candidate; certification can promote
it; `route.py` then exact-matches a future dot and replays those frozen steps
without a model.
Evidence: `bank/extractor.py`; example skill card; `bank/route.py`. [S18, S19, S08]

**13. How many repetitions before something is certified? Who chose that
threshold and why?**
[High confidence] There are two regimes. Map probe certification defaults to 5
fresh runs with a >=4/5 rule. Skill certification currently uses an oracle gate, 3
identical stability replays, then 20 deterministic probes; status becomes
certified when the Wilson lower bound is >=0.70. The 0.70 floor is a
project/spec choice, and the repo itself calls it a "magic number" that future
metabolism work should replace; the per-skill error-budget formula is not active
because frequency/cost data are not populated.
Evidence: STATUS map certification; `bank/certify.py` constants; Campaign Record
notes theta=0.70 as magic number. [S02, S09, S04]

**14. What's a Wilson interval doing in my agent, in plain English?**
[High confidence] It is trying to prevent "5 wins means 100% reliable" thinking: a
Wilson interval gives a conservative range for an unknown success probability when
you only observed a small number of successes/failures. That is sensible for
stochastic fresh-run probes. In the current skill certifier, however, 20
deterministic replays of essentially the same seed are not 20 independent samples
of the real world, so the interval should not be marketed as broad reliability
confidence until the probes vary independently.
Evidence: `certify.wilson` and `bank/certify.py` probe implementation. [S09]

**15. Can it learn a wrong thing confidently? What is stopping it?**
[High confidence] Yes, if the verifier or task specification is wrong. What stops
simple reward hacking is strong: candidates must work on a fresh seed, fail on a
deliberately broken copy, remain stable, and later replay their own check; planted
flaws were convicted in the campaign. What is not solved is semantic
specification: a perfectly stable predicate can certify the wrong objective, and
current Queen Chat can also fail to bind the natural-language answer to the proved
fact.
Evidence: `banking.confirm`; E2 discrimination; current chat gate. [S10, S04, S07]

**16. Does learning transfer - does a skill from domain A help in domain B, or is
everything siloed?**
[High confidence] Current execution transfer is conservative and mostly siloed:
`route.py` matches certified skills by exact normalized statement identity, not
semantic similarity. EQUIP showed inheritance can change exploration depth within
its experimental task family, but there is no evidence that a skill learned in
unrelated domain A automatically transfers to domain B.
Evidence: `bank/route.py` exact statement matching; E1d 12x result. [S08, S04]

**17. What does "12x deeper exploration" mean concretely, and would it replicate
on someone else's machine?**
[High confidence] Concretely, the final trial recorded 63 mutation/boundary-probing
rules from equipped agents versus 5 from cold agents, and frontier reach held in
12 of 13 equipped arms across three trials. That is a measured experimental
result, not "12x smarter." The repo bundles the artifacts, but I found no
independent reproduction; model/service randomness and environment details mean
replication on another machine is an open question until an external group reruns
the frozen protocol.
Evidence: README/Campaign Record. [S01, S04]

### Memory

**18. "Memory that metabolizes" - what does that mean beyond a folder of YAML
files?**
[High confidence] In the code that exists, it means more than static files but
less than the full metaphor: every certified-skill invocation can update
`last_used`, invocation count, stability and a provenance delta; sleep can harvest
candidates, re-certify and schedule stale cards. The full generative metabolism -
compressed traces, regeneration, competition, grounded crystallization and
demotion - is not built.
Evidence: `queen/reconsolidate.py` + `sleep.py`; metabolism spec statuses.
[S16, S17, S05]

**19. What's the difference between this and RAG, stated without metaphors?**
[High confidence] RAG retrieves stored text/chunks and puts them into a model
context so the model can generate an answer. Current Dot Maps skill memory
exact-matches a trigger to a stored executable procedure and deterministic check,
then can execute it with zero model calls. The proposed C1 "regenerate from
compressed traces" memory is a different idea, but it is explicitly not built yet.
Evidence: `bank/route.py`; metabolism C1 status. [S08, S05]

**20. If it regenerates memories, how do I know it's not hallucinating them? Show
me the mechanism, not the vibe.**
[High confidence] Today it does not regenerate memories, so there is no
implemented mechanism to show. The metabolism spec proposes an evidence ladder:
hard facts must match append-only provenance, structural claims must be
consistent with it, and only connective tissue may be regenerated freely. That is
a design requirement, not a shipped end-to-end recall path. Current certified
skills avoid this problem by replaying frozen steps/checks instead of
regenerating them.
Evidence: metabolism C1 NOT BUILT, C2 built but pointed at wrong target; `route.py`
deterministic replay. [S05, S08]

**21. What gets forgotten, when, and can forgetting lose something I needed?**
[High confidence] Current Dot Maps does not really forget records: logs and YAML
skill cards persist. Decay can make a skill due for recheck, but there is no
implemented delete-to-trace or general demotion path. So automatic forgetting is
not currently a data-loss risk; manual deletion or a future demotion system is.
The future C1/C6 design must preserve provenance/recovery because intentional
record deletion could otherwise lose needed details.
Evidence: metabolism C1/C6; reconsolidate/sleep. [S05, S16, S17]

**22. Where does my data live? Can I read it, edit it, delete it, move it?**
[High confidence] Most project state is ordinary local files: `maps/`, `skills/`,
`runs/` JSONL, Queen home/config JSON, and user-side MCP bindings under
`~/.config/dotmaps`. You can read, edit, delete and move those files, but editing
evidence or certified artifacts can invalidate hashes/provenance and should be
treated as a new version. Data can leave the machine when you use hosted
Claude/API models, HTTP Watch/fetch, or remote MCP servers; scripted/Ollama paths
can remain local.
Evidence: README layout; ToolBox bindings; Queen paths; hosted/local drivers.
[S01, S11, S15]

**23. The generative-memory claim (seeds, 10x compression) - built, or
aspirational? Which experiments prove which parts?**
[High confidence] Aspirational for the 10x/generator claim. The metabolism spec
explicitly marks C1 generator storage as NOT BUILT and makes >=10x storage
reduction a future falsification test. What is built/demonstrated is procedural
skill banking, model-free replay, write-on-read metadata, deterministic
re-certification and some decay scheduling. None of the Dot Maps experiments
prove 10x generative-memory compression or faithful reconstruction after deleting
original records.
Evidence: metabolism C1 status and T-A; Queen reconsolidation; EQUIP.
[S05, S16, S04]

### Cost & the model question

**24. When exactly is a model called vs not? Show me the decision point in code.**
[High confidence] Queen Chat calls `route_first()` first. If a known workflow is
fully covered, it returns a $0 reply and never invokes the runner. Otherwise it
falls through to `run_work_order()`, which launches `claude -p`. `bank/route.py`
itself reports `model_calls=0`. Watch and sleep are mechanical/no-model paths. The
core traveler separately calls a model only when its configured driver is `llm` or
`ollama`; scripted traversal uses none.

```
covered = route_first(message, ...)
if covered is not None:
    return covered          # $0, no model

order = run_work_order(...) # claude -p on frontier chat
```

Evidence: `queen/chat.py:138-152` and `318-369`; `bank/route.py`; `sleep.py`;
`traveler.py`. [S07, S08, S17, S11]

**25. What did the whole system cost to build and run? What does a month of use
cost?**
[High confidence] The repository does not contain enough information to price the
whole build: human labor, Claude subscriptions, hardware, electricity and all
pre-campaign calls are not accounted for. It records about $60 for the Aug 2-7
EQUIP campaign, $0.50 for grow-005, and $0.0776 for the Queen OS live chat work
order. As of this audit, Anthropic lists Claude Pro at $20/month billed monthly
and includes Claude Code, while API use has separate token pricing. A defensible
monthly Dot Maps number therefore depends on how many frontier tasks require a
model versus certified replays; the repo has not measured a normal month.
Evidence: Campaign Record; README; Queen live flight; official Anthropic pricing
current 17 Aug 2026. [S04, S01, S14, S22]

**26. Can it really run on a small local model? Has that been measured or
asserted?**
[High confidence] Measured for execution, not for general learning.
qwen2.5-coder:7b completed the 5-dot migration and probe-certified it 5/5; local
7B/14B attempts at the POKE learning loop failed before the frontier Claude run
succeeded. Other assays found an 8B floor and 14B saturation. So the supported
claim is "a small local model can execute some dense, well-specified maps," not
"small local models can learn arbitrary new skills."
Evidence: README and STATUS experiment layer. [S01, S02]

**27. If Anthropic changes Claude Code's pricing or behavior tomorrow, what
breaks?**
[High confidence] Queen frontier chat/work orders are coupled to the `claude` CLI,
a hard-coded model name, command flags, stream/json output fields such as
`subtype`/`num_turns`/`total_cost_usd`, and subscription authentication. Those
paths can break if the CLI contract changes. The core verifier, bank, replay,
scripted traveler, Ollama traveler and Watch do not inherently depend on
Anthropic and would keep working.
Evidence: `queen/chat.py`/`workorder.py` and traveler drivers. [S07, S12, S11]

**28. "Free forever" - what's the catch? Storage? Re-verification compute? My
electricity?**
[High confidence] "Free" means zero model-token charge on a covered replay. You
still pay local CPU, storage, electricity, network, any remote-service costs,
periodic deterministic verification, and the cost of learning new frontier
skills. If you need Claude Code to acquire or repair a skill, the
subscription/usage cost returns. The phrase is directionally true for model
inference, not total cost of ownership.
Evidence: README pay-once claim; `route.py`; `sleep.py`. [S01, S08, S17]

### Trust & verification

**29. Who verifies the verifier? If a check is wrong, everything downstream is
confidently wrong - what catches that?**
[High confidence] The system tries to verify verifier behavior with an oracle
gate: it must pass intact state, fail a deliberately broken state, and be stable;
maps also have attack tests. That catches vacuous or brittle checks, not a
semantically wrong requirement. A verifier can be perfectly discriminating about
the wrong thing. The missing outer layer is an independent hidden
oracle/human specification review plus mutation/metamorphic tests against
realistic faults.
Evidence: `bank/certify.py` oracle gate; README attack floor. [S09, S01]

**30. The hash chain - tamper-evident or tamper-proof? What can a malicious me
still do?**
[High confidence] Tamper-evident, not tamper-proof. Editing/deleting/reordering an
existing line without recomputing later hashes is detected. A malicious owner
with write access can rewrite the entire file and recompute every hash, replace
the verifier/code, delete the log, or roll back to an earlier copy. There is no
external signature/transparency anchor. In addition, concurrent legitimate
writers can currently fork the chain because appends are not locked.
Evidence: `queen/trips.py` hash chain implementation. [S20]

**31. You graded your own experiments - has anyone independent reproduced even
one?**
[High confidence] I found no evidence of an independent reproduction in the
public repository. GitHub currently shows 0 forks and 0 stars, and the campaign
evidence is project-run. That does not invalidate the results, but it means
"reproducible artifacts are public" is the accurate claim; "independently
reproduced" is not.
Evidence: GitHub repo stats and public campaign. [S01, S04]

**32. What's the worst bug the system has caught in itself? The worst it
missed?**
[High confidence] Among the strongest self-caught failures: a live weak traveler
rewrote its protected source during migration and the source hash refused
certification; the grow loop exposed 18 counterfeit/vacuous rules; the 3B
repeatedly fabricated success while the board stayed red. The worst correctness
bug I found that the current assurance suite misses is the Queen Chat proof
boundary: structural `answer.json` can pass and its free-form answer can be
returned before the predicate is truly confirmed. Security-wise, the
un-sandboxed full-agent work order and SSRF surface are more severe operational
risks.
Evidence: STATUS, README, `queen/chat.py`, `workorder.py`, `traveler.py`.
[S02, S01, S07, S12, S11]

**33. If I gave it a subtly poisoned task description, what happens?**
[High confidence] If the poison changes the acceptance criteria, Dot Maps can
reliably certify the poisoned objective - a classic specification attack. If the
poison is content a full agent reads, it can also act as prompt injection. The
current architecture has strong enforcement after an objective is frozen, but
weaker provenance/authorization for deciding whether that objective is the right
one. The fix is signed/inherited objective provenance, explicit human approval
for material acceptance-criteria changes, and prompt-injection-resistant
tool/data separation.
Evidence: Inference from compile/workorder objective construction and
sovereign-verifier model. [S12, S01]

### Agents & autonomy

**34. What can it do without asking me? What must it ask about? Who drew that
line?**
[High confidence] Within a map, the traveler can autonomously use only declared
ToolBox capabilities and budgets; destructive actions have explicit gating in the
core harness. Queen can replay covered skills, run Watch checks and sleep/re-cert
without model calls. New paid chat work begins because the user asked; larger
workflows use explicit authorization/escalation. The boundary is
maintainer-authored policy in maps/gatekeeper/specs, not a universal formal
side-effect policy, and the full Claude work order currently escapes the narrower
ToolBox model.
Evidence: STATUS safety layer; ToolBox; workorder money law; Queen trip
vocabulary. [S02, S11, S12, S20]

**35. The work order runs a full agent with tools on my machine - what stops it
from `rm -rf`, emailing someone, or spending money?**
[High confidence] Not enough today. The code assumes cwd confines the agent and
launches Claude Code with `--dangerously-skip-permissions`. That protects the
committed seed only because work starts from a disposable copy; it does not
mechanically prevent Bash from addressing other filesystem paths, using host
network tools, reading inherited environment variables, or invoking authenticated
CLIs available on the machine. Anthropic itself recommends sandbox/isolation for
bypass-permission modes. This is a P0 before unattended use.
Evidence: `queen/workorder.py`; `queen/chat.py`; Anthropic Claude Code security
docs. [S12, S07, S23]

**36. How does it decide to give up? Has the abort governor ever fired in real
use, or only in backtests?**
[High confidence] There are hard budgets (cycles, max turns, wall-clock timeout)
and a governor that classifies WALL/CHURN/DIRECTIONAL behavior with a persistence

Evidence: Queen flight log governor backtest; workorder constants; campaign.

**37. Multiple agents at once - coordination, collision, or not supported?**
[High confidence] Not supported as a mature feature. The research specs

**38. If it runs overnight, what's the blast radius of a 3am failure?**

### Security & privacy

**39. Threat model: who's the attacker - the model, the internet, a malicious
prompt in a watched webpage?**
[High confidence] All of them should be in scope: (1) a reward-hacking/mistaken
model; (2) malicious task/spec author; (3) hostile or prompt-injecting internet
content; (4) compromised/hostile MCP endpoint; (5) local user tampering; (6)
dependency/CLI changes; and (7) accidental concurrent writers. The existing
project is strongest against model self-report/reward hacking and much less
complete against network/specification/host-compromise threats.
Evidence: README attacks/safety plus audit of network/workorder paths.
[S01, S11, S12, S13]

**40. It crawls sites and reads my folders - what leaves my machine, ever?**
[High confidence] Hosted model paths can send the prompt and whatever file/tool
content the agent reads to the hosted provider; Watch/fetch sends HTTP requests to
target sites; remote MCP calls send data to the bound MCP server; the UI
currently references Google Fonts; and credentials may be used to authenticate
those services. Scripted and Ollama traversal plus purely local verification can
stay local. The product should surface a per-action egress label instead of
making users infer this from the driver.
Evidence: traveler hosted/Ollama drivers; MCP; Watch; Queen UI commit.
[S11, S13, S14]

**41. Are the certified skills executable code? Can a poisoned skill enter the
library and replay forever?**
[High confidence] Skill cards are declarative YAML procedures, not arbitrary
LLM-written source code; they contain allowed tool steps and a check, and
generated dot check scripts come from deterministic templates. That reduces
code-injection risk. A poisoned semantic skill can still be certified if its
check encodes the wrong truth and then replay whenever its exact trigger matches.
Re-certification reduces stale-state risk, but it does not fix a poisoned
specification.
Evidence: `bank/extractor.py`; banking compiled check template; `route.py`.
[S18, S10, S08]

**42. Secrets, tokens, credentials - how are they handled during work orders?**
[High confidence] The dedicated `dotmaps connect` path is comparatively careful:
hidden token entry, chmod-600 storage/binding and live handshake validation are
documented. The full work-order path is the weak spot: it only removes
`ANTHROPIC_API_KEY` and passes the rest of `os.environ` to Claude Code. A
Bash-capable agent may therefore see unrelated secrets. Use an allowlisted empty
environment and explicit per-tool credential injection.
Evidence: STATUS connect implementation; `queen/workorder.py`/`chat.py` env
construction. [S02, S12, S07]

### Research standing

**52. What is genuinely novel here vs well-executed assembly of known ideas
(Voyager, proof-carrying code, FSRS)? Name your prior art yourself before someone
else does.**
[High confidence] Prior art is substantial: Voyager demonstrated an
ever-growing executable skill library plus environment feedback/self-verification;
proof-carrying code established the producer/proof/host-policy pattern; testing,
mutation/metamorphic testing and CI provide executable oracles; event
sourcing/hash chains provide replay/audit; RAG/procedural memories provide
retrieval; FSRS provides decay/review scheduling. The plausible novelty is the
specific combination and empirical discipline: per-dot world-state promises with
a verifier sovereign over model self-report; discriminating bank-time gates
against reward-hacked checks; certified procedural replay as a model-free
execution rung; and a preregistered program measuring how inherited verified
knowledge changes agent exploration. That is an interesting research
contribution, but novelty has not been peer-reviewed or established against a
comprehensive literature search.
Evidence: Dot Maps repo plus Voyager, PCC, FSRS references. [S01, S25, S26, S27]

### The uncomfortable ones

**56. Why hasn't a lab with a thousand engineers built this? What do you know
that they don't - or what constraint are they respecting that you're ignoring?**
[High confidence] Large labs have built many ingredients - agent evals, sandboxes,
executable tests, tool permissions, skill/memory systems - so the right answer is
not "they missed the idea." Dot Maps makes a different trade: it gives up
generality wherever necessary to obtain a hard oracle. The constraint big general
assistants cannot ignore is verifier/specification cost: many useful real-world
tasks do not have cheap ground truth, and a wrong oracle can be worse than an
uncertain model. Dot Maps is interesting precisely if it proves that enough
recurring work can be converted into cheap, trustworthy oracles to justify that
trade.
Evidence: Inference from prior art + repo architecture. [S01, S25, S26]

**57. Where's the moat when the oracle patterns are visible in a public repo?**
[High confidence] The code/oracle pattern itself is a weak moat under MIT. A
defensible moat would have to come from a large corpus of verified real-world
workflows and failures, high-quality domain-specific oracle libraries,
longitudinal drift/re-cert data, integrations and trust, independent benchmark
reputation, and a UX that makes specification cheap. If those do not accumulate,
a well-funded team can reproduce the mechanics.
Evidence: Strategic inference; repo is MIT and public. [S01]

**58. If I could only keep one piece - the instrument, the metabolism, or the
queen - which survives and why?**
[High confidence] Keep the instrument. It is the piece with the clearest
independent value, strongest evidence and simplest falsifiable claim: agents do
work; world-state verifiers decide whether it is done; receipts replay. Queen is
a replaceable product shell, and the full metabolism is still largely a research
program. The instrument can exist without either; neither is credible without the
instrument.
Evidence: README/STATUS versus metabolism status and Queen recency.
[S01, S02, S05, S14]

**59. What would make you abandon this?**
[High confidence] Abandon or radically narrow the thesis if independent
multi-domain tests show any of these persist after honest engineering:
verifier/specification creation costs more human effort than the repeated work it
saves; certified skills do not reduce silent failure versus ordinary tests; drift
makes certificates stale faster than re-verification can economically keep up;
useful tasks rarely admit cheap external oracles; or safe sandboxing/credential
isolation removes the autonomy/economics that made Queen compelling. Those are
thesis-level failures, not bugs to patch around.
Evidence: Recommended falsification criteria.

**60. Two years in: what has it actually done for you - the builder - that
justifies the next two?**
[High confidence] The public Dot Maps record does not support a claim that this
repository itself is two years into operation; the documented Dot Maps experiments
are concentrated in July-August 2026, while the metabolism spec references
earlier adjacent ideas. What the repo demonstrably delivered to the builder is
already meaningful: multiple caught agent failure modes, a live $0 local
migration, a killed efficiency hypothesis instead of a spun result, a 52-pair

The builder's personal ROI beyond the public artifacts is not something the

## Audit recommendations

### What I would change before merging queen-os into main

1. Repair the Queen Chat proof boundary first. A user-visible answer must not
   exist until the model process succeeded, the typed fact is validated, the
   predicate is executed, the discriminating gate passes, and the rendered reply
   is derived from that checked result.
2. Move every full-agent work order into OS-level isolation. Treat Claude Code as
   untrusted code execution: disposable filesystem mount, no host home, no
   inherited secrets, network deny-by-default, explicit egress/tool grants,
   CPU/memory/turn/time budgets.
3. Replace direct urllib fetch with one SafeFetcher used by Watch and traveler
   fetch. Block non-public IP space and unsafe redirects/DNS behavior; add a
   security test matrix.
4. Make evidence journals concurrency-safe. Use a process-safe append
   transaction, unique monotonic sequence, fsync, and a stress test. If product
   state grows, use SQLite WAL for state while keeping hash-chained JSONL as
   signed/anchored evidence export.
5. Redesign skill certification so probes are independent. Fresh copy per
   skill/probe; isolate mutations; declare what population the success
   probability represents. If deterministic replay is all you want, report
   consistency rather than a statistical confidence bound.
6. Fix re-cert semantics: only reset freshness after a passing re-cert;
   convict/demote on failure. Make stability actually change recheck interval
   instead of cancelling algebraically.
7. Attach formation context and invalidation conditions to every skill. The
   skill should know which dataset/site/schema/tool version it was certified
   against and which change forces re-cert.
8. Hash persistent IDs from full normalized identity. Keep readable slugs only
   as prefixes.
9. Add a model/agent adapter interface around Claude Code instead of embedding
   CLI fields in product logic. Pin/test supported Claude CLI versions and fail
   with a compatibility message.
10. Add external replication as a release gate for research claims. One
    independent rerun of E2 and one multi-domain version of the repeat-cost/
    silent-failure experiment would materially change the project standing.

### Concrete new regression tests to add

- Chat `answer.json` has a valid path/predicate name but a false value -> user
  must receive no asserted answer.
- Chat answer text contradicts a true structured fact -> deterministic renderer
  must prevent contradiction.
- Claude result `subtype != success` but `answer.json` exists -> work order must
  be failed.
- Two threads/processes append 1,000 trip/chat events concurrently -> chain
  remains linear, unique, complete.
- Watch URL is localhost, 127.0.0.1, ::1, RFC1918, link-local, cloud metadata,
  redirect-to-private, DNS-rebind simulation -> all blocked.
- Work order sees planted `SECRET_TOKEN` in parent env -> child environment does
  not contain it.
- Due skill fails oracle on re-cert -> status convicted, no `reset_after_recert`,
  no "re-certified" success trip.
- Mutation skill A cannot mutate the seed used to certify skill B; reorder skill
  files -> identical certificates.
- Same host / different Watch path -> distinct watcher IDs; long same-prefix
  questions -> distinct chat map IDs.
- Certificate context fingerprint changes -> route refuses stale skill until
  re-cert.

### Recommended positioning language

> **Use this sentence publicly.** Dot Maps is an agent-verification harness that
> lets models do work but gives completion authority to executable world-state
> checks, then preserves verified procedures for auditable, model-free replay.

> **Avoid this sentence for now.** "A self-learning autonomous OS with verified
> memory that runs free forever." The individual ideas point in that direction,
> but current code/evidence does not yet support the combined general claim.
